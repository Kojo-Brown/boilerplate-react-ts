# Internationalisation

One `IntlProvider`, two locales, and a lint rule that makes a physical CSS side
impossible to write. The reason the third item is in that sentence is the whole
argument of this document: translating strings is the visible half of i18n and
the easy half, and a perfectly translated application whose layout does not
mirror is not usable by the reader it was translated for.

- `src/shared/i18n/` — the layer
- `src/pages/i18n-lab/` — every capability on one page, `/labs/i18n`
- `tooling/eslint/logicalProperties.ts` — the right-to-left gate
- `tooling/i18n/stylesheetDirection.ts` — the same gate for `globals.css`
- `e2e/i18n.spec.ts` — the parts only a browser can answer

## The locale list, and why the second one is Arabic

`en-GB` and `ar-EG`. A list of `en-GB` and `de-DE` would exercise message lookup
and nothing else: both are left-to-right, both pluralise on one/other, both write
Western digits. Every defect this layer exists to prevent is invisible under such
a pair —

| Defect                              | Invisible in `de-DE` | Obvious in `ar-EG`                                          |
| ----------------------------------- | -------------------- | ----------------------------------------------------------- |
| `margin-left` in a component        | yes                  | the element is on the wrong side                            |
| a sentence assembled from fragments | mostly               | word order differs and the fragments cannot be reordered    |
| `count === 1 ? "item" : "items"`    | yes                  | wrong for 2, for 3–10 and for 11–99                         |
| a number interpolated as a string   | yes                  | Western digits where Eastern Arabic-Indic ones are expected |

— so the second locale is the one that finds them.

Adding a third is `SUPPORTED_LOCALES`, a catalogue file, and a loader entry. The
catalogue is typed `Record<MessageId, string>`, so an incomplete one is a compile
error rather than a page that is _mostly_ translated.

### A locale is not a currency

`LocaleDescriptor` carries a tag, a direction and an endonym. It deliberately
does not carry a currency, and this is the one rule in here worth arguing about
before changing: a price in pounds is £12.34 whether the page is in English or
Arabic. A locale-keyed currency silently converts nothing while appearing to
convert everything, which is the worst available failure mode for a number people
act on. So currency is passed with the amount:

```ts
intl.formatNumber(amountMinor / 100, { style: "currency", currency });
```

The lab shows the consequence: switching to Arabic changes the digits, the
grouping separator and the symbol's spelling (`UK£`), and does not change the
amount.

### The endonym is not a translated name

The switcher labels each locale in its own language — `العربية`, not "Arabic".
A reader looking for Arabic is by definition someone who may not be able to read
the current UI language, so a translated label fails exactly the person using the
control. Each `<option>` carries its own `lang` and `dir` so a right-to-left name
renders as itself inside a left-to-right list.

## Types: three things the compiler checks

`src/shared/i18n/formatjs.d.ts` fills in react-intl's `FormatjsIntl` namespace,
which narrows every call site in the program at once — there is no wrapper to
route calls through and no import to remember, so a `formatMessage` written by
somebody who has never opened that file is still checked.

| Hook         | Effect                                                                          |
| ------------ | ------------------------------------------------------------------------------- |
| `Message`    | `formatMessage({ id })` and `<FormattedMessage id>` take a known id only        |
| `IntlConfig` | `intl.locale` is `"en-GB" \| "ar-EG"`, not `string`                             |
| `Formats`    | `{ format: "medium" }` is a compile error; the declared names are the only ones |

`MessageArguments` — which would type each message's _placeholder values_ — is
left empty on purpose. v12 infers those only from `defineMessages<V>(…, { typed:
true })` where `V` is written out by hand, and feeding it back through
`MessageArgumentsFromCatalog<typeof catalog>` is a type cycle: the catalogue's ids
are checked against `Message.ids`, which would then be `keyof MessageArguments`,
which is derived from the catalogue. TypeScript reports "recursively references
itself as a base type" and the whole namespace collapses to `any`. Writing the
argument shapes by hand instead would make every placeholder a second source of
truth beside the ICU string that already declares it. What catches a missing
value is the provider's `onError`, which throws outside production — so it fails
a test rather than a customer — plus `catalogs.test.ts`, which formats every
message in every locale at six different counts.

## The load path

```
main.tsx
  └── await resolveI18n()           negotiate, then load the catalogue
        ├── readStoredLocale()      an explicit choice wins outright
        └── negotiateLocale(navigator.languages)
  └── createRoot().render(<I18nProvider initialLocale initialMessages>)
```

The catalogue is resolved **before** the first render, and the alternatives are
each wrong in a way a reader experiences:

- A provider that negotiates internally renders one commit in the default locale.
  For a right-to-left reader that is the entire layout drawn mirrored and then
  re-drawn.
- A Suspense fallback is a blank screen whose duration is a network fetch.

For the default locale there is no fetch at all: `en-GB` is statically linked
because it is the fallback, and a fallback that has to be fetched is not a
fallback — it is a second thing that can fail, at the moment something has
already failed. Every other locale is an `import()` and gets its own chunk, so
adding a language costs the initial bundle nothing. `e2e/i18n.spec.ts` asserts
that the Arabic chunk is not requested until it is asked for.

A rejected catalogue load starts the application in the default locale and
reports. A stale `index.html` against a new deploy is the ordinary way a chunk
404s; it resolves itself on the next load, and a blank page is not a defensible
response to it.

### Switching, after the first render

`setLocale` is a `useTransition`, so the current page stays interactive while the
new catalogue is fetched and both the messages and the direction commit together.
A half-applied switch — direction changed, messages not — is the one outcome worse
than no switch at all.

The state update after the `await` is wrapped in `startTransition` a second time,
which is not redundant: React 19 ends the transition scope at the first suspension
point, so an update made after it would commit outside the transition.

A switch also announces itself, in the new language, through the app's existing
live regions. Without that a screen-reader user has every string on the page
replaced and is told none of it. It is in the new language because a reader who
chose it is the one person guaranteed to understand it.

### Storage

The choice goes in `localStorage` under `locale`, and only when the reader makes
it — never the negotiated value. Recording the negotiated locale would make a
first visit permanent and silently stop honouring a changed browser setting.

Every read is validated, because the value outlives the build that wrote it: a
locale dropped from `SUPPORTED_LOCALES` is still in the browser of everyone who
chose it, and an unvalidated read hands that tag to `Intl` (a `RangeError`) and to
the catalogue loader (`undefined is not a function`) on the visit _after_ the
removal.

**Server rendering changes this.** A server has to know the language before it
writes the first byte, which `localStorage` cannot tell it. The preference moves
to a cookie, `resolveI18n({ preferred })` takes the parsed `Accept-Language`
header — which is why `preferred` is a parameter — and `negotiateLocale` is
unchanged.

## Negotiation

RFC 4647 lookup, narrowed to what a two-level tag needs:

1. exact tag, case-insensitively
2. same language, any region
3. fallback

The loop is over _requested_ tags in the outer position. A reader whose list is
`["de", "ar"]` gets Arabic; iterating the supported list first would answer with
whichever of ours is declared earlier, which is a preference belonging to the
developer rather than to the reader. The inner fallthrough is per requested tag as
well: `["ar-SA", "en-GB"]` resolves to `ar-EG` on rule 2 rather than reaching
`en-GB` on rule 1, because the difference between two Arabics is vocabulary and
the difference from English is literacy.

There is no `Intl.LocaleMatcher`. `localeMatcher: "lookup"` is an option on the
formatters and resolves against _their_ data, not against an application's
catalogue list, so it cannot answer "which of my two translations should this
reader get".

## Writing a message

- **One message per sentence.** Never assemble a sentence from fragments at the
  call site: word order is not a constant across languages, and a fragment gives a
  translator no grammatical context.
- **Plurals through ICU `plural`, never `count === 1`.** English has two forms,
  Arabic has six. A ternary in a component can only ever be right about one
  language.
- **Numbers and dates through the formatters.** A bare `{count}` in Arabic prints
  Western digits; `#` inside a plural and `{value, number}` elsewhere go through
  `Intl.NumberFormat`, which knows better.
- **Ids are `area.thing`, not the English text.** Text-as-id reads beautifully
  until the copy changes: "Sign in" → "Log in" becomes a rename across every
  catalogue, and ids stop being stable identifiers at the moment translators are
  relying on them to be.
- **Interpolate the brand, do not translate it.** `document.title` is
  `"{page} · {app}"`, one message, so the separator and the order of the two halves
  are the translation's to decide.

### What `catalogs.test.ts` enforces

Types cover "every catalogue has every id". The tests cover the contents:

| Check                     | The defect it catches                                                 |
| ------------------------- | --------------------------------------------------------------------- |
| every message parses      | a malformed string renders as raw ICU on a page that looks translated |
| `isStructurallySame`      | a renamed, dropped or invented placeholder — a throw at render time   |
| plural categories vs CLDR | a category absorbed by `other`, which is grammatical in no language   |
| formats at six counts     | an error raised while formatting a branch no other test selects       |

The parser is pinned to the version `react-intl` itself depends on: a gate reading
a different AST than the renderer can be wrong in both directions.

## The right-to-left pass

`<html dir>` mirrors every _logical_ CSS property in the document and nothing
else. So one physical `margin-left` left behind is a gap in the mirror — with no
type error, no failing test, and no visual symptom in the language its author was
looking at. The only way to keep it correct is to make the physical spelling
unavailable.

### `i18n/logical-properties`

An ESLint rule over class strings: the literals inside a `className` attribute and
inside a `cn()` / `clsx()` / `twMerge()` call. Class strings and not the file,
because "left" and "right" are ordinary English words and ordinary key names —
`ArrowLeft`, "the queue on the right" — and a rule that reported those is a rule
that gets switched off within a week. Comments are not literals, so prose about
`ml-4` is not a finding.

Two kinds of finding:

**A utility with a logical twin** is always wrong, and the message names the
replacement with the variants, the negation and the importance marker put back, so
it can be pasted:

| Physical                                  | Logical                                        |
| ----------------------------------------- | ---------------------------------------------- |
| `ml-*` `mr-*`                             | `ms-*` `me-*`                                  |
| `pl-*` `pr-*`                             | `ps-*` `pe-*`                                  |
| `left-*` `right-*`                        | `start-*` `end-*`                              |
| `border-l*` `border-r*`                   | `border-s*` `border-e*`                        |
| `rounded-l*` `rounded-r*` `rounded-tl*` … | `rounded-s*` `rounded-e*` `rounded-ss*` …      |
| `text-left` `text-right`                  | `text-start` `text-end`                        |
| `float-left` `clear-right` `scroll-ml-*`  | `float-start` `clear-inline-end` `scroll-ms-*` |

**A utility with no logical twin** can only be qualified. `translate-x-*` is the
whole list: there is no `translate-inline-start`, so "off screen towards the edge
it is anchored to" is a negative X in a left-to-right document and a positive X in
a mirrored one. The rule accepts it once it carries an `ltr:` or `rtl:` variant,
which is the author stating which direction they meant. `translate-x-0` is exempt —
zero displacement is the same displacement either way, and `md:translate-x-0` is
how the sidebar says "on a desktop, in flow".

The sidebar is the one place in the application where a direction is named twice:

```tsx
sidebarOpen ? "translate-x-0" : "ltr:-translate-x-full rtl:translate-x-full";
```

A bare `-translate-x-full` hides the drawer correctly in English and slides it
_across the page_ in Arabic, arriving off the far edge having travelled over the
content.

### `tooling/i18n/stylesheetDirection.ts`

The same gate for `globals.css`, which ESLint cannot parse. It scans for physical
properties (`margin-left`) and physical values on logical properties
(`text-align: left`), skipping comments and anything inside a rule whose selector
already names a direction — `[dir="rtl"] .drawer { … }` is the deliberate escape
hatch, for the handful of properties with no logical form at all.

The stylesheet passes today, which is why the gate was written today. A gate added
after the first regression is a gate added while somebody is arguing about whether
to fix it.

### What neither gate can see

An inline `style={{ marginLeft }}`, a third-party component's own stylesheet, and
anything positioned by JavaScript. `e2e/i18n.spec.ts` measures the sidebar's
bounding box in both directions, which is the assertion that fails if a physical
side survives both gates — jsdom lays out nothing, so it cannot answer this.

## Testing

| Harness                               | For                                                   |
| ------------------------------------- | ----------------------------------------------------- |
| `renderWithIntl(ui, { locale })`      | a component in a given language                       |
| `renderWithProviders(ui, { locale })` | the same, with the store, query client and API client |
| `RouteTransitionHarness locale=…`     | anything that navigates                               |
| `intlFor(locale)`                     | an `IntlShape` for the pure functions that take one   |

All of them use the real `I18nProvider` rather than a bare `IntlProvider`, because
most of what is worth testing about this layer is the provider's own behaviour:
`<html dir>`, `<html lang>`, the announcement on switching, and `useI18n`.

Neither passes an `onError`, which is the point: the provider re-throws outside
production when nothing is listening, so a malformed message or a missing
placeholder value fails the test that rendered it.

`setup.ts` resets `<html lang>` and `<html dir>` after every test — jsdom keeps one
document per file, so an Arabic test would otherwise leave the document
right-to-left for whatever renders next, and a later assertion about direction
would pass for the wrong reason.

## The bundle

i18n is a first-load cost and the budget gate exists to put that number in front
of a reviewer rather than to forbid it. This work raised three ceilings:

| id            | before   | after    | what moved                                           |
| ------------- | -------- | -------- | ---------------------------------------------------- |
| `chunk.intl`  | —        | 14.8 kB  | new: `react-intl` + `@formatjs` + the ICU parser     |
| `chunk.index` | 130.3 kB | 133.7 kB | the provider, the switcher and the `en-GB` catalogue |
| `initial.css` | 8.87 kB  | 9.6 kB   | the logical utilities and the two `rtl:` variants    |
| `initial.js`  | 190 kB   | 208 kB   | the sum of the above: **+16.6 kB gzip**              |

`chunk.intl` is split for cacheability, not to move a number — the runtime
releases on its own cadence, so an app deploy should not invalidate it in a
returning reader's cache, which is why `router` and `redux` are split too. It buys
nothing on first load, and `initial.js` is budgeted to say so.

The ICU parser is the largest single part and cannot currently be dropped:
pre-compiling messages to AST at build time removes the need for it at runtime, but
`intl-messageformat` still imports it statically, so it stays in the graph either
way.

## What is not done

The application's **page copy is still English literals**. What is translated is
the shell — nav labels, the sidebar landmark, the skip link, every route title,
the document title and the arrival announcement — plus the i18n lab. The
twenty-odd other lab pages hold their text inline, and `LiveRegionsLabPage` still
has a hand-rolled `count === 1` plural that this document tells you not to write.

That is a deliberate boundary rather than an oversight: the layer is what makes
the conversion possible, the conversion is a per-page task with a per-page
catalogue, and a half-converted page is worse than an unconverted one. The same
applies to `formatMoney` in `features/checkout/checkoutApi.ts` and the two
`formatCurrency` helpers in `entities/report/`, which are still pinned to
`en-GB`/`GBP`: they are domain modules with their own suites, and moving them onto
`intl` means threading a locale through a state machine.

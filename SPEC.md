## Phase 9 — React 19 Concurrency

- [x] `useTransition` + `useDeferredValue` on a heavy filterable list, with a jank before/after benchmark — `<ConcurrentFilterList>` plus a `/labs/concurrency` harness and a Playwright benchmark that drives both arms. The memo boundary around the rows turned out to be load-bearing: without it the urgent render still reconciles every row and deferring buys almost nothing (840ms vs 1232ms worst keypress-to-paint, against 256ms vs 824ms with it). The benchmark is what caught that (PR #19)
- [x] `useOptimistic` mutations with automatic rollback on failure — `useOptimisticList` plus `<OptimisticTaskList>` and a `/labs/optimistic` harness whose fake server fails on demand from the URL. Nothing undoes an optimistic action: the rollback is the _absence_ of a commit, so both layers run through one reducer and a rejected request simply never reaches committed state. Three React 19 behaviours were not obvious and are now pinned by tests — the `await` must stay inside the transition; ordinary state set synchronously inside an async transition never renders on its own (clearing the error there left a stale banner up through the next request _and_ kept the optimistic layer alive past its settle point, which is what three failing tests were actually reporting); and optimistic actions unwind as a group, so an overlapping failed mutation's row lingers until the last in-flight action settles (PR #20)
- [x] `use()` API for unwrapping promises and context inside Suspense boundaries — `<UserProfileCard>` reads data with `use(cache.read(id))` and its cache with `cache ?? use(ProfileCacheContext)`, the conditional read no other hook-shaped API allows; `<ProfilePanel>` supplies the two boundaries `use()` needs, per profile, and `/labs/use` drives both against a fake service configured from the URL. Four things were not obvious: a promise created during render suspends forever, so `createPromiseCache` is the precondition rather than an optimisation; a rejected entry has to be sticky, because dropping it hands the retry a fresh _pending_ promise and the tree falls back forever instead of surfacing the error (so retry is `invalidate` then reset — reset alone visibly does nothing); replacing the cache in place is an update, and React Router runs navigations in a transition that holds the previous UI, so the lab remounts on a `key` instead; and a cached rejection nobody reads is an unhandled rejection. Testing Library's `render` wraps the first render in a _synchronous_ `act()`, which strands a `use()` retry and leaves the fallback up until `waitFor` times out — `lazy()` never hit it — so `src/test/renderSuspense.tsx` adds `renderAsync`/`actAsync` (PR #21)
- [x] Actions API: `useActionState` + `useFormStatus` replacing manual form submit state — `<InviteTeammateForm>` keeps no submit state of its own (no `isSubmitting`, no `setError`, no `try/finally` resetting a flag), with `src/shared/lib/formState.ts` as the reusable half: one `FormState<Field>` shape that a schema failure and a server rejection both resolve to, so the form renders one thing instead of branching on where the problem came from. `InviteRejectedError.field` decides whether a message belongs under a control or at the top of the form, so that judgement is made by the side that can make it. Three React 19 behaviours were not obvious and are now pinned by tests: React resets the form once the action settles, which is right for a success and hostile on a failure — the action echoes the submitted values back and the controls read `defaultValue` from there, so the reset restores what was typed rather than wiping it; `<select>` is the one control that echo does not reach, because React keeps an input's and textarea's `defaultValue` in sync after mount but never propagates a changed one onto a mounted select's options, so the reset restores the option selected at _mount_ and the choice disappears silently on the failure path only (found by a failing test, fixed by keying the select on the echoed value); and `useFormStatus` reports only to descendants of the `<form>`, so calling it in the component that renders the form returns `pending: false` forever with no warning — hence `<SubmitButton>` and `<SubmittingNotice>` as separate components, with the button's test asserting the idle reading from outside the form. Focus moves to the first invalid control keyed on the state object, since narrowing that dependency to `state.status` breaks the second identical submission. `/labs/actions` drives it against a fake service configured from the URL. 731 tests across 78 files, all six checks green (PR #22)
- [x] React Compiler enabled incrementally with an ESLint rule and a memo-removal audit — `annotation` mode, so a function is compiled only where it opts in with `"use memo"`; `reactCompiler.config.ts` is the one object Vite, Vitest, ESLint and the audit gate all read. Vitest previously loaded no Vite plugins at all, so the unit suite ran _uncompiled_ source — every "safe to delete this `useMemo`" claim would have been unfalsifiable, and each stability test added here was checked to fail with its directive removed. `eslint-plugin-react-hooks` 5→7 brings the compiler's own 17 diagnostics in as lint rules; run across the codebase for the first time they found exactly two real things: `useStableCallback` wrote a ref during render (fixed in a `useLayoutEffect` — it cannot be rebuilt on React 19.2's `useEffectEvent`, which is rejected outright when returned from a custom hook), and TanStack Virtual makes `VirtualList` uncompilable, which is why it is deliberately outside the cohort. `ToastProvider` is the clearest case for the compiler: `toast` and `dismiss` were each wrapped in `useCallback` and then passed inside a fresh `{{ toast, dismiss }}` literal every render, so consumers compared a new object every time and both memoizations achieved nothing. The audit gate exists because a failed compile is _silent_ — the compiler logs a `CompileError` and emits the function unchanged while the build stays green — so `tooling/reactCompiler.audit.test.ts` asserts every opted-in function reaches `CompileSuccess` and that no un-annotated file is compiled at all. 742 tests across 79 files; `useMemoCache` present in the production bundle (PR #23)
- [x] Suspense-driven data fetching with streaming boundaries and nested fallbacks — `SectionBoundary` (a Suspense boundary and the error boundary that has to be outside it) plus `createSectionCache`, a promise cache for a page of differently-typed sections so `read("breakdown")` stays `Promise<BreakdownRow[]>` rather than a union every component then narrows. `/labs/streaming` renders one report under all four combinations of boundary layout × prefetching, with a live request timeline. Boundary placement was expected to be purely a display concern and is not: a suspension abandons the render pass it happened in, so under a single boundary the breakdown suspending means the activity feed never renders and therefore never requests — three round trips in series where nesting a boundary per sibling gives two, and prefetching above the shell's boundary gives one. That claim is measured (`wereConcurrent` over a recorded event timeline), not assumed. Three more behaviours are pinned because they are easy to get backwards: a nested fallback is a sequence rather than a stack (nothing inside an unresolved boundary has rendered, so the inner boundaries do not exist yet); sibling boundaries reveal in completion order, not source order, with no stable way to hold a fast one back since `<SuspenseList>` is still experimental; and a flat boundary's retry has to invalidate every section it stands in front of, or the reset renders the shell straight back over a still-rejected entry and rethrows in the same frame. Tests state their ordering instead of arranging it — `createDeferredReportApi` settles only when the test says so — after the first latency-based draft failed four assertions on its first loaded run. The same race then failed CI in the pre-existing `UserProfileCard`/`ProfilePanel` fallback tests, which are converted to a gate here rather than given a wider timer. 825 tests across 91 files (PR #24)
- [x] `startTransition` for route changes to keep the old UI interactive during navigation — the transition was already there: react-router 7.18 wraps its own state updates in `React.startTransition`, so every `<Link>` click always was one and adding another around `navigate()` changes nothing. What decides whether the previous page survives is where the Suspense boundary is. A transition preserves already-revealed content, and "already revealed" belongs to a boundary _instance_ — a boundary first mounted by this navigation has nothing revealed in it, so React commits its fallback immediately. Every route carried its own boundary, which made the outcome depend on whether React happened to reconcile two route elements onto the same one: `/` ↔ `/about` shared an instance and held; `/dashboard` behind `<ProtectedRoute>` and the `*` fallback did not and flashed. Nothing in the route config showed which. `RootLayout` now holds one boundary above `<Outlet>` and the routes under `/` carry none; `RouteFallback` picks the skeleton by pathname, so hoisting does not cost the per-route skeletons, and reading `useLocation()` there is sound because a fallback only renders when the boundary is new — during an in-app navigation it never renders at all. Two behaviours were not obvious and are pinned against React and React Router directly: the `await` in `startTransition(async () => { await navigate(to) })` is load-bearing and its absence is _silent_ — `navigate` returns before the router touches React state, so the sync form's scope has closed by the time the update lands and `isPending` is never true; with lazy-only routes it still navigates and still holds, so the only symptom is a progress bar that never appears, and adding a loader to any route is what makes it bite. And `useNavigation()` cannot drive that bar at all: it tracks loaders, and a `React.lazy` chunk is not one, so it reads `idle` for the entire download — `<NavLink>`'s `isPending` has the same source, hence `isPendingTarget` beside it rather than shadowing it. Holding is not shippable alone: a click on a slow route otherwise produces no visible change whatsoever, which reads as the app having ignored it, so `RoutePendingBar` is the other half rather than decoration. `/labs/navigation` drives both boundary placements against a deliberately slow route, with a click counter because a held page and a hung page are identical in a screenshot. 909 tests across 99 files, 24 Playwright tests including an arm asserting the per-route boundary still loses the page, all six checks green (PR #25)

## Phase 10 — Advanced Patterns & Architecture

- [x] Compound components with context: `<Tabs><Tabs.List><Tabs.Panel>` and a typed slot API — `createTabs<TValue>()` rather than a generic root with statics hung off it, because the statics do not share the root's type parameter: `Tabs.Tab` is a separate function with its own generic and nothing in TypeScript relates it to the instantiation of the JSX element it sits inside, so `<Tabs.Tab value="typoo">` infers `"typoo"` and compiles clean — a tab that matches no panel, selecting a value nothing answers to, with no error at any level. Closing over `TValue` in a factory is what makes the slots share one union; spelling the root's props as a union of the controlled and uncontrolled shapes makes `value` without `onValueChange` and `value` alongside `defaultValue` unwritable in the same move. Six `@ts-expect-error` assertions pin all of it, with `tsc` as their assertion runner — they fail `typecheck` and `build`, not `test`. Three behaviours were not obvious and are pinned by tests: arrow-key order is read from the DOM at keydown rather than from a registry tabs write to on mount, because mount order stops being DOM order the moment a tab is conditional — reveal one mid-row and it appends, so ArrowRight from its left neighbour jumps to the end (`querySelectorAll('[role="tab"]:not(:disabled)')` also gets reordering and disabled-skipping for free); the roving tab stop follows focus rather than selection, since under manual activation the two diverge by design and binding it to the selection silently discards where the user arrowed to, invisible under automatic activation which is why it ships broken; and `aria-controls` is set only on the tab whose panel is actually in the document, since inactive panels unmount by default and setting it everywhere leaves dangling IDREFs (`keepMounted` renders them `hidden` instead, and then every tab's reference resolves). `createTabs` must be called at module scope, and that is not left to discipline — `react-hooks/static-components` rejects a call inside a component and rejected the first draft of the type-assertion block before it ever ran. 930 tests across 100 files, all six checks green (PR #26)
- [x] Headless component pattern: behaviour hooks split from presentation — `useListbox` holds the behaviour (selection, virtual focus, arrow keys, Home/End, typeahead, ARIA) and renders nothing; `OptionList`, `SelectMenu` and the `CardGrid` in `/labs/headless` render it three ways, the last of which is a grid of cards rather than a list at all. `useListbox.test.ts` has no JSX in it and `listboxSkins.test.tsx` runs one behaviour suite against two skins — the split is what makes both possible. Four things about the prop getters were not obvious: spreading one is not merging (`{...getOptionProps(v)} onClick={x}` silently drops the hook's handler and the other order drops the caller's, hence `mergeProps` and getters that take caller props); the opt-out cannot be `event.preventDefault()`, since stopping page scroll under ArrowDown is the commonest thing a caller's key handler does and reading the DOM flag would leave the arrow keys dead with nothing to chase, so `preventHookDefault` is a separate marker in a `WeakSet`; `TBase & TCaller` is unusable as the return type because TypeScript reduces an intersection to `never` on the first conflicting property, making every _other_ prop an error too (`Omit<TBase, keyof TCaller> & TCaller`, with a `Record<never, never>` default so a no-argument call is not `unknown` throughout); and React 19 stops calling a ref callback with `null` once it returns a cleanup, so a merged callback owns unwinding the refs that have none — load-bearing in `SelectMenu`, where the popup's focus ref and the hook's scroll ref share an element. Two listbox behaviours are pinned because they are easy to get backwards: virtual focus is re-derived from the live options every render, or `aria-activedescendant` keeps naming an id that has been filtered out; and Space commits the active option only when no typeahead is in flight, since "New " is how you reach "New York" past "New Hampshire". `aria-activedescendant` never moves real focus so nothing scrolls on its own, and jsdom defines no `scrollIntoView` at all — `e2e/headless-listbox.spec.ts` presses End against an overflowing list in a real browser. Each of those three claims was checked against the failure it names. 1020 tests across 106 files, all six checks green (PR #27)
- [x] Polymorphic `as` prop with full generic type inference — `PolymorphicProps` in `src/shared/lib/polymorphic.ts`, with `Text` (constrained `as`) and `Button` (open `as`) as the two worked examples. The pattern is worth revisiting rather than copying because React 19 removed its hard part: `forwardRef` infers its props parameter once at the call site, so a generic render function handed to it comes back non-generic and `<Box as="a" href>` errors on a valid prop — every library shipped a hand-written generic call signature cast over the result to work around it. With `ref` an ordinary prop, a plain generic function is the component and the cast is gone, not replaced. Three type-level things were not obvious and are pinned by `@ts-expect-error` blocks that `tsc` runs rather than vitest: `Omit<A | B, K>` is built from the keys A and B _share_, so omitting one key from `ComponentPropsWithRef<"a" | "button">` discards both `href` and `disabled` — and a union reaches the parameter from something as ordinary as `as={admin ? "a" : "button"}`, hence `DistributiveOmit`; own props and element props must be joined by subtraction, since `TOwnProps & ComponentPropsWithRef<TElement>` reduces to `never` at the first conflict (`Button`'s `size` against `input`'s numeric `size`) and takes every _other_ prop on the tag down with it, the same trap recorded in `mergeProps.ts`; and `as` must be destructured, because React writes an unrecognised lowercase prop straight through and `as` is real on `<link>`, so a forwarded one lands as a literal `as="h2"` with every role, text and style assertion still passing. Making `Button` polymorphic forced an accessibility fix rather than a rename: `loading` is meaningful on every element `as` can name but `disabled` exists on five tags only, and forwarding it emits an anchor carrying `disabled` — written without complaint by React, honoured by no browser — so the link greys out and stays focusable, activatable and navigable. `Button` therefore owns `disabled` and picks the mechanism the element supports, `aria-disabled` plus a click interceptor where the attribute does not exist (which covers the keyboard too, since Enter on a focused anchor dispatches a click). Two claims were checked against the failure they name: the first ref assertion could never have fired, because DOM interfaces are structural and `HTMLHeadingElement` declares only a deprecated `align` that `HTMLInputElement` also has, so the assertion pairs label ← paragraph instead; and `<Button as="input">` throws whether or not children are passed, since the `{loading && <svg />}{children}` slot is always two expressions — recorded as a limitation rather than fixed, because a submit input can hold neither a label nor a spinner. The E2E arm exists because jsdom implements no navigation at all, so a jsdom test passes whether or not `preventDefault` ran; every disabled click there is a `force` click, since Playwright's own actionability check reads `aria-disabled` as not-enabled and would never dispatch an event. 1053 tests across 109 files, 30 Playwright tests, all six checks green (PR #28)
- [x] Render-prop and HOC patterns documented with their modern-hook equivalents — one capability ("does this media query match?") delivered three ways, because a translation table nobody can run is a claim rather than a demonstration: `useMediaQuery` is the implementation and `<MediaQuery>` and `withMediaQuery` are twelve-line adapters over it, rendered side by side at `/labs/render-props` and driven across a real breakpoint by Playwright, which jsdom cannot do — it implements no media queries at all, so every unit test here answers from a harness the tests themselves control. `withBoundary` is the counterexample the doc needs, the HOC with no hook equivalent, stated as a contrast rather than an assertion: a component that renders the same boundary _from inside itself_ and then throws does not catch its own error, because a hook runs inside the component that calls it and both halves of a boundary are about that component from the outside. Four things were not obvious and are pinned by tests. A HOC built during render returns a new function every call, so React replaces the fiber instead of updating it — state discarded, effects re-run, DOM nodes and focus rebuilt, and nothing reported anywhere; `react-hooks/static-components` catches it now and reports at the _usage_, not at the call that built the component, so a disable comment on the assignment is flagged as unused while the error stays. Carrying the wrapped component's statics in the return type has to go through an `Omit`: the obvious `ComponentType<…> & TStatics` intersects the inner component's _call signature_ back in, JSX resolves against that instead, and every call site errors demanding the injected prop again — `HoistedStatics` works precisely because an omitted object type has no call signature, and both halves are asserted with `@ts-expect-error` since the wrong fix makes one of them look right alone. Hooks called inside a render prop attach to the _provider's_ fiber, so a provider that invokes its children conditionally changes its own hook count between renders and React throws, naming a component from another file, with no lint rule able to see it. And `useMediaQuery` is a `useSyncExternalStore` rather than state plus an effect because the effect form loses any change landing between the first read and the listener attaching — the test reproduces that race by flipping the query at the instant the listener is added, and the naive implementation was checked against it: it fails that test and the query-change one and passes the other five. 1097 tests across 115 files, 33 Playwright tests, all six checks green (PR #29). Not done: `ThemeContext` still tracks `prefers-color-scheme` with its own effect-and-state subscription and has both defects this hook fixes — a behaviour change to the theme system, so it is recorded in `docs/render-props-and-hocs.md` rather than folded in here.
- [x] State machines with XState for a multi-step checkout flow — the argument is not that a checkout has steps, it is that it has invariants, and a machine is the only shape that enforces one instead of re-asserting it at every call site: `cart` has no eligible `next` while the basket is empty, `submitting` declares no `order.place` so a second click is not a transition rather than a click somebody remembered to debounce, and exiting `submitting` stops the invoked actor and fires its `AbortSignal`, so cancelling cancels the request instead of ignoring its result. Four things were not obvious and are pinned by tests. A guard on its own produces a _dead button_: XState drops an event with no eligible transition — no error, no snapshot change, nothing in a devtools timeline — so `next` guarded only by `shippingValid` gives a Continue that does nothing at all on an invalid form; every guarded step therefore carries a second, unguarded transition to record the refusal, listed last because transitions are evaluated in array order, and both run the _same_ action, since splitting it into a commit half and a show-errors half gives each one a branch the guard already ruled out. Entry actions run _after_ the transition's actions, so the tidy-looking `entry: "clearMessage"` would erase the very rejection that routed the user back to that step, silently and only on the path least likely to be exercised by hand. `confirmed` is not `type: "final"`, because a final root state stops the actor and a stopped actor cannot be restarted — the flow ends there, the actor modelling it does not. And v5 has no typestates: a snapshot in `review` is not a type that knows `context.shipping` is non-null, so `toCheckoutInput()` narrows once behind a `detailsComplete` guard and the impossible branch is a real branch a test covers rather than a non-null assertion nobody can check. A rejection can also belong to a step — `CheckoutRejectedError` carries `step` and `retryable`, so a declined card lands back on payment with the reason attached instead of on an error screen offering a Try again that would decline identically, and that button is not rendered when `order.retry`'s guard would refuse it. On the React side `useSelector` narrows the subscription and `memo` narrows the render, and `CheckoutTotal` needs both: it sits inside a component that re-renders on every keystroke, and a re-rendering parent re-renders its children whatever they subscribe to. 1219 tests across 127 files, 38 Playwright tests, all six checks green (PR #30). Not done: the machine is not persisted, because restoring into `submitting` needs an idempotency key on the server rather than a client-side change.
- [x] Feature-Sliced Design directory refactor with an import-boundary lint rule — all 260 source files moved into `app → pages → widgets → features → entities → shared`, with `fsd/layer-imports` (`tooling/eslint/fsdBoundaries.ts`) failing the build on an import going up or sideways. The rule is the point rather than the directories: a layout is a claim about which parts of the code can change independently, and one import turns `shared/ui/Button` from a component anyone can use into one that only works when the auth feature is present — type-checking, testing green and building the whole time. It enforces layer order, slice isolation, that no file sits loose in a sliced layer, and that nothing outside `src/test/` imports test scaffolding. `import type` is exempt from the first two, which is the line being drawn rather than a softening: an erased import cannot put a higher layer in a lower layer's bundle or create a runtime cycle, and the coupling it does leave is coupling the type checker reports at every affected site — sound only because `consistent-type-imports` makes a type-only import impossible to spell as anything else. Three real inversions came out of applying it, each previously invisible: `RootLayout` imported `RouteFallback`, so the shell depended on every page it could host (now a required `fallback` prop, required rather than defaulted to a spinner because a forgotten one still renders, just without the per-route skeletons that boundary exists to keep); `QUERY_ERROR_EVENT` was exported from the module constructing the `QueryClient` singleton, so learning an event name meant importing the singleton (moved to `shared/api/queryEvents.ts`); and `app/main.tsx` started the MSW dev worker out of `src/test/`, so the entry point reached into test scaffolding (handlers moved to `shared/mocks/`). The elevated coverage floor follows the files it guarded — `src/shared/lib/**` and `src/shared/hooks/**` keep theirs and `src/entities/**` and `src/features/**` gain one, since that is where the API modules, caches and schemas landed. 1253 tests across 128 files, 38 Playwright tests, coverage marginally above the pre-move baseline at 94.27% lines / 92.23% branches, all six checks green. The rule was checked against the failures it names: four deliberate violations in real files each produced exactly one error, and the new floors were probed the same way. Not done: slice public APIs are not enforced, so a cross-layer import can still name a file inside a slice rather than its barrel; and `app/api/client.ts` still reaches for the store singleton, which is legal where it sits and is what the next item is about (PR #31)
- [x] Dependency inversion: swap the API client via context for tests and Storybook — the client had no callers at all, and that was the symptom rather than an oversight: it lived in `app/` and imported the store singleton for `state.auth.token` and `logout()`, so no module below the top layer could import it (an upward import is a lint error), no test could reach the refresh path without mutating global store state, and the `isRefreshing` flag plus resolver queue were module-level, so a 401 raised through one client could be resumed by a refresh another client had started. The contract now sits at the bottom of the graph (`shared/api/apiClient.ts`: `ApiClient`, `ApiError`, `SessionPort`) and the instance stays at the top; `app/api/storeSession.ts` is the only module that knows both HTTP and Redux, and `app/api/client.ts` is nothing but the construction. The context default is `null`, not the real client: a working default lets a component rendered outside the provider issue real requests from a green suite, which is the failure the seam exists to remove, and `renderWithProviders` extends that with a no-route stub so an unplanned request names the route it wanted. ## Phase 11 — Performance Engineering

- [x] Web Workers via Comlink for CPU-bound parsing off the main thread — the claim is not that the parse gets faster. It does not: the same 200,000 rows take ~150ms either way, and both arms of `/labs/workers` run the _same_ function (`parseTransactionsCsv`) over the same seeded bytes, which is what removes "the results differ" as an explanation for anything the stats show. What changes is that those 150ms stop being a frame: the blocking arm records 2 frame intervals with a worst of 133.4ms at an effective 13.3fps, the worker arm 33 intervals with a worst of 16.8ms at 60.0fps, and both numbers are attached to every Playwright run. Six things were not obvious and each is pinned by a test. A microtask yield makes cancellation impossible, silently — chunking is what lets a `cancel` land, but only across a _task_, since microtasks drain before the event loop takes its next one; the suite runs the loop both ways against a cancel sent immediately and the microtask arm parses all 5,000 rows having never seen it and returns a correct result, which is exactly why nothing about it looks wrong. `scheduler.yield()` is the wrong fix (it resumes the continuation _above_ newly queued tasks, backwards when the message you are waiting to hear is "stop") and so is a `MessageChannel` ping (same task source as the message it exists to let through), leaving `setTimeout(…, 0)` and its ~4ms nesting clamp — the reason the chunk is thousands of rows and not tens. An `AbortSignal` cannot cross the boundary at all, so cancellation is a job id plus a separate `cancel` call, and that clone failure is asserted in the browser rather than in a unit test because **jsdom does not reproduce it**: under Node's `structuredClone` a jsdom signal clones happily into a plain object, so a unit test would have asserted the opposite of the truth. A callback must be `Comlink.proxy`-wrapped and TypeScript will not say so — `Remote<T>` types a remote method's parameters with the _local_ types, so the bare form type-checks and throws `DataCloneError` at runtime, discovered because an `@ts-expect-error` on that line failed the build as an unused directive. The side that must release a proxied callback is not the side that made it: Comlink stands up a `MessageChannel` per proxy and closes neither end unless the _receiver_ asks, so the worker releases in a `finally` and the test counts `MessagePort.close()` across three parses, the only observable the platform offers. The amounts array is transferred rather than cloned, which detaches the sender's buffer — asserted from both sides at once. And an error's class does not survive (only its name does), so `instanceof CsvHeaderError` is false on the receiving side and the client re-wraps into `CsvParseError` with the original on `cause`. Two more came out of building it, each checked against the failure it names: hoisting `new URL("./x.worker.ts", import.meta.url)` into a `const` one line above the `new Worker` call makes `vite build` emit **no worker chunk at all** and exit 0, leaving a `new Worker` pointing at a path that exists only under `pnpm dev`; and the jank meter has to be stopped a frame _after_ a blocking parse, since stopping inside the same callback discards the long interval and reports a worst frame of 16.7ms — which is what the first version of the benchmark did, and it made the two arms look identical. jsdom has no `Worker`, so `src/test/workerChannel.ts` drives the real Comlink protocol over a `MessageChannel` and the client and lab page take a worker _factory_ — `docs/dependency-inversion.md`'s seam applied to a thread; mocking Comlink would have removed every failure above. 1433 tests across 142 files, 46 Playwright tests, coverage 96.19% statements / 93.80% branches with every threshold met, all six checks green (PR #33). Not done: the two `shared/workers/` modules sit at 0% coverage, since they can only run inside a real `Worker` — the entry point is one `exposeCsvParser` call and the factory one `new Worker`, with the behaviour where the tests can reach it, and no coverage exclusion was added to hide them.
- [x] Windowed infinite scroll with TanStack Virtual + intersection prefetch — virtualisation breaks the usual sentinel rather than composing with it: the standard one is rendered after the last row, and under windowing the last row is not in the DOM until you have scrolled to it, so the observer has nothing to say until the user has already arrived. The sentinel therefore sits _after the virtualiser's spacer_ — always mounted, exactly at the end of the scroll range, 1px tall — and `rootMargin` moves the trip point without moving the element. Three things were not obvious and each was checked against the failure it names. The observer's root must be the scroll container: `rootMargin` grows _the root's_ box, so against the default root a bottom margin asks how far past the browser window a sentinel clipped inside a 480px inner scroller is, a question that never comes true — nothing throws, the list still loads, and prefetch has silently degraded to loading at the bottom, indistinguishable from working on a fast connection. The observed element has to be state rather than a ref: a `useRef` read in an effect sees `null` on the only pass that effect runs, because the sentinel does not exist until `hasNextPage` does, and a ref assignment schedules no render, so there is no second pass and the observer is never created — swapping the state back for a ref fails 10 of the hook's 14 tests. And loading is driven by intersection _state_ in an effect, not by the observer callback: an observer reports transitions, and "the page landed and the sentinel is still in view" is not one, so every page shorter than the prefetch margin stalls the chain with no boundary crossed and nothing to indicate why; dropping `isFetchingNextPage` from the effect's dependencies fails the unit test and takes the E2E arm from five pages to exactly two. The E2E also corrected a claim rather than confirming one: its first version asserted the feed would run to completion with no scrolling, and it does not — the chain stops once the loaded rows exceed the window plus the margin, which is stopping for a reason rather than not stopping at all, and both the test and the doc now say so. `getItemKey` is required rather than defaulted to the index because the virtualiser caches a measured height per key, which makes index keys a claim about positions rather than rows; `flattenFeedPages` de-duplicates by id for the other half, since a cursor is a position in a feed still being written to and a duplicate virtualiser key is two indices sharing one cache entry with nothing reporting it. jsdom implements neither `IntersectionObserver` nor `ResizeObserver` and has no layout for either, so `src/test/intersection.ts` and `src/test/virtualizerMock.ts` carry every non-geometric claim and a real browser carries the rest: a flat DOM row count across 300+ loaded rows, a spacer covering the whole dataset, and the two prefetch distances behaving differently at the identical scroll position. 1520 tests across 148 files, 52 Playwright tests, coverage 96.31% statements / 93.93% branches with every threshold met, all six checks green (PR #34). Not done: scroll restoration (needs the cursor and the offset persisted, plus a virtualiser told to skip to an index before its rows are measured), prepending (needs scroll anchoring), and page eviction — memory grows with rows loaded even though the DOM does not, and TanStack Query's `maxPages` would bound it at the cost of re-fetching on scroll-up.
